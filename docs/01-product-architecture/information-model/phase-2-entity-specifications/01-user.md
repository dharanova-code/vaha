
# Information Model

## Phase 1. Domain Model v1.1

**Status:** **Approved & Frozen**

### Applied Architectural Refinement

**Notification** has been removed from the Core Domain.

**Reason**

Notifications do not possess independent business meaning. They are delivery mechanisms that communicate meaningful events originating from other domains.

Notifications are therefore reclassified as an **Application Service**, not a domain entity.

They may be generated by:

* Capture
* Device
* Insight
* Backup
* Connected Service

As a result:

* ✅ Removed from the Core Entity Catalog
* ✅ Removed from the Entity Relationship Diagram
* ✅ Removed from the Object Hierarchy
* ✅ Removed from Domain Boundaries

# User

**Status:** Draft for Review

# Purpose

The **User** entity represents the single owner of the Vaha ecosystem.

Its purpose is not authentication or identity management. Its purpose is to establish ownership, responsibility, and continuity across all user-created information.

Within the domain model:

> **Everything meaningful ultimately belongs to a User.**

The User entity is therefore the root aggregate of the entire product.

---

# Ownership

The User owns:

* Capture
* Device
* Collection
* Tag
* Insight
* Settings
* Backup
* Connected Service

No other entity may exist without an owning User.

This rule ensures ownership remains explicit throughout the product.

---

# Responsibilities

The User entity is responsible for:

* Establishing ownership.
* Defining personal preferences.
* Controlling privacy decisions.
* Granting or revoking optional external services.
* Organizing personal knowledge.
* Maintaining continuity across the Vaha ecosystem.

The User entity is **not** responsible for:

* Capture processing.
* Device behavior.
* Insight generation.
* Synchronization.
* Search.
* Notifications.

Those responsibilities belong to their respective domains.

---

# Attributes (High-Level)

Only conceptual attributes are defined at this stage.

### Identity

Represents the user's identity within Vaha.

---

### Ownership Context

Defines that all personal entities belong to this user.

---

### Preferences

Represents durable personal preferences.

Detailed preference definitions belong to the Settings entity.

---

### Privacy Decisions

Represents user-approved privacy choices, including optional cloud participation.

The implementation of these decisions belongs to other entities.

---

### Connected Services

Represents relationships with optional external services.

---

### Profile Context

Represents human-readable identity information that personalizes the experience without affecting ownership.

---

# Relationships

## User → Capture

One User owns many Captures.

Captures cannot exist without a User.

---

## User → Device

One User may own one or more trusted Vaha devices over time.

A Device never owns the User.

---

## User → Collection

Collections are created and managed by the User.

---

## User → Tag

Tags are defined by the User and reused across Captures.

---

## User → Insight

Insights belong to the User because they are derived from the User's captures.

---

## User → Settings

Exactly one Settings entity exists for each User.

---

## User → Backup

Backups preserve user-owned information.

---

## User → Connected Service

Connected Services extend the user's experience through explicitly approved relationships.

---

# Lifecycle

The User lifecycle is intentionally stable.

### Created

The user begins using Vaha.

Ownership is established.

---

### Active

Normal operating state.

The user owns and manages personal knowledge.

---

### Suspended

Temporary state where access or participation may be limited without affecting ownership.

---

### Archived

The user has intentionally preserved their information without actively using the product.

---

### Removed

The user permanently removes their relationship with Vaha.

Ownership ends only after explicit confirmation and completion of applicable data handling policies.

---

# State Model (High-Level)

```text
Created
    ↓
Active
    ↓
Suspended (optional)
    ↓
Active
    ↓
Archived (optional)
    ↓
Removed
```

State transitions are intentionally minimal because the User entity should remain highly stable.

# CRUD Responsibilities

### Create

Establish user ownership.

---

### Read

Access ownership context and user-related information.

---

### Update

Modify user-controlled information and preferences.

---

### Delete

End ownership through an explicit, intentional process.

Deletion should never occur implicitly.

---

# Offline Behaviour

The User entity is fully available offline.

Ownership does not depend on internet connectivity.

All user-owned information remains accessible according to local ownership rules.

Offline operation is the default behavior.

---

# Sync Behaviour

Synchronization is an extension of ownership, not a replacement for it.

When cloud synchronization is enabled:

* Local ownership remains primary.
* Synchronization reflects user decisions.
* The User entity remains conceptually unchanged.

Synchronization must never redefine who owns data.

---

# Privacy Rules

Privacy is inherent to the User entity.

Core principles:

* The user owns all personal information.
* External sharing requires explicit consent.
* Cloud participation is optional.
* Ownership remains understandable at all times.
* Privacy decisions belong to the user, not the system.

---

# Validation Rules

The User entity must always satisfy the following conditions:

* Exactly one owner exists for every domain object.
* Ownership must remain internally consistent.
* Privacy choices must be explicit.
* Removal actions require deliberate confirmation.
* A User cannot exist without ownership responsibility.

---

# Business Rules

### Rule 1

Every core domain entity must belong to exactly one User.

---

### Rule 2

Ownership cannot be transferred implicitly.

---

### Rule 3

Cloud participation never changes ownership.

---

### Rule 4

Privacy preferences always override optional connected services.

---

### Rule 5

Removing a User requires explicit handling of owned information.

---

### Rule 6

A User may choose to remain entirely local without reducing product capability.

---

# Future Extensibility

The User entity should support future capabilities without changing its core responsibility.

Examples include:

* Multiple trusted Vaha devices.
* Optional family or shared environments, if introduced with clear ownership semantics.
* Portable user profiles.
* Cross-device continuity.
* Additional connected services.
* Future identity providers.

These extensions must preserve the principle that ownership is singular and explicit.

---

# Architectural Notes

## Root Aggregate

The User is the root aggregate of the Vaha domain.

Every ownership relationship ultimately originates here.

---

## Ownership Before Identity

The model prioritizes **ownership** over authentication.

How a user signs in is an implementation concern.

Who owns the data is a domain concern.

---

## Stable by Design

The User entity should evolve very slowly.

Most future product growth should occur in child entities rather than the User itself.

---

## Local-First Foundation

The User exists independently of cloud services.

Local ownership is the architectural default.

Cloud capabilities extend the experience without redefining the entity.

---

## Source of Truth

The User entity establishes the foundational principles that every subsequent entity specification must follow:

* Single ownership.
* Explicit responsibility.
* Local-first operation.
* Privacy by default.
* Clear domain boundaries.
* Long-term stability.

With this specification, the **User** entity becomes the **frozen source of truth** for ownership and identity across the entire Vaha Information Model. Subsequent entity specifications (starting with **Capture**) should inherit these principles rather than redefine them.
